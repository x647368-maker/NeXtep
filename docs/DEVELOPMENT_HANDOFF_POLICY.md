# 台前调度开发与交接规范

本规范自 v0.9.73-dev（versionCode 88）起适用于所有版本和开发窗口。GitHub 是工程状态的事实来源。当前总工程见 [PR #123](https://github.com/x647368-maker/NeXtep/pull/123)。

## 开始或恢复开发

1. 读取对应 PR、最新交接评论、远端分支与准确 HEAD。核对基线、提交差异、尚在运行的 CI、失败日志、测试产物与历史保护清单。
2. 从最新有效检查点接续。对照源码与测试证据确认已完成范围，复用已经完成的实现。遇到与聊天摘要不一致的情况，以 GitHub 的实际提交和可核验结果为准。
3. 由总协调窗口负责整合。专项成果先在授权分支审查。禁止擅自修改 main、覆盖历史版本、改变包名或现有签名。

## 保存有效阶段

- 每完成一个有效阶段，立即将可复核的成果提交到对应 GitHub 分支，并在对应 PR 写明准确 commit、改动、仍未解决的问题、实际测试结果、证据链接和下一步。
- 出现连接中断、限流或额度不足时，优先保存已验证成果和续作起点。能记录时将未推送或未验证工作明确标注在 PR。新窗口根据 PR 和源码恢复。
- 提交应对应可检查的阶段成果。避免重复开发、重复研究、重复构建未受影响且已通过的版本，以及没有工程内容的提交。

## 测试与交付

- 对受改动影响的功能执行回归。记录测试命令或工作流、实际运行结果、准确提交、设备或模拟器及系统版本。
- 分开记录源码审计、编译、单元测试、模拟器运行、真机验收。GPU 事务 ACK 仅证明提交状态。真机显示、性能、功耗及 OEM 兼容性需要相应运行证据。
- 候选 APK 使用原签名，交付前验证证书 SHA-256、包名、版本名、versionCode 和 APK SHA-256。未经用户真机验收不得公开发布。
- 用户负责安装原签名候选及真机反馈。源码、构建、测试、分支和打包由开发窗口完成。
