# 台前调度 v0.9.26 后续：阻塞问题与跨 AI 精确验收（2026-11-11）

状态：**不符合稳定交付门槛**。本分支是独立候选，不能标记完美修复，不能自动发布酷安或 Releases。不得因单元测试通过而假定 ColorOS 真机已完成验收。之前的签名内测 APK 也不等于本分支最新构建。

## 1. 在线更新：客户端能查，不等于服务端已发布

- N5 用户截图：实际安装 `0.9.18-dev` / versionCode 33；DEV、STABLE 两个渠道均报「暂无可验证的更高版本」。
- `atomic-update-feed/index.json` 当前 `releases=[]`；公开 GitHub Releases 目前只看到早期 0.1.0-dev debug APK，没有最新候选的配套 `atomic-update.json`。
- `UpdateChecker` 要求版本码更高、当前渠道、固定包名、固定证书、SHA-256、文件大小与已签名 APK；不能将聊天文件/Actions 未签名产物伪装成可在线升级的 Release。
- 自动同步 Release 元数据的 GitHub workflow 在独立 PR #6 草稿中，**默认 main 尚没有对应工作流**，故发 Release 也不会自动更新 feed，除非管理员随后完成隔离 PR 的校验和安全合并。
- `UpdateCoordinator.maybeCheck` 只在打开 App 且到了间隔时检查，不是每 12 小时全天候推送；通知权限不解决服务器无可验证资产的问题。
- 本轮不冒险上传未验收候选；只有用**当前证书、同包名、新 versionCode** 的正式验收包（若用户已安装 41，则更新必须 code > 41）发布并验证完整清单后，才可打通真实更新提醒。

- `RELEASE_NOTES.md` 的 0.9.25、0.9.26 标题前加 `v`；原 `StageEmbeddedReleaseNotes.parse/archived` 用前面不允许字母的正则错误排除这两条。
- 修复版接受 `v` / `V` 或无前缀，仍必须精确匹配 versionName 和 versionCode，不接受 0.9.260 代替 0.9.26。
- 增加 JVM 测试覆盖「现装 0.9.26、归档 0.9.25、旧版 0.9.24、错码/串号」。
- 增加 `scripts/verify-release-notes-version.py` 作为 CI 构建门禁：仓库 RELEASE_NOTES.md、Gradle APK `versionName/versionCode`、已注入 SystemUI `StageRuntimeIdentity.BUILD` 三者相互一致。原 SystemUI 标记长期滞留在 `0.9.18/33-integrated-candidate`，这次纠正。
- **本功能是构建时打包离线说明，不是远程实时同步**。新版本的所有说明不能在未升级 APK 的旧客户端里自行出现。不得再宣传为“已完成实时自动同步”。

## 3. 性能与电池：可证实数据/无法证实原因

两份用户真实报告：OnePlus PMS110，Android17，`0.9.25-dev`，2026-11-11。
- 17:37–17:52：67→68% 电量、39.1→39.8°C、4 小窗、+31,371 帧事件、+3,685 任务查询、+56 预览截取、SystemUI 进程 CPU +3,549,764ms。
- 17:57–18:12：68→69% 电量、39.8→40.0°C、4 小窗、+39,887 帧事件、+2,830 任务查询、+32 预览截取、SystemUI 进程 CPU +3,525,366ms。
- 报告原「充电状态=1」实际是 `BatteryManager.EXTRA_PLUGGED=AC`，**并非充电状态**，不能用电量上涨证明省电。修复后的报告区分外部电源类别和真正 BATTERY_STATUS。
- `Process.getElapsedCpuTime()` 统计**整个 SystemUI 进程**，900 秒累计约 3.5e6ms，相当于约 3.9 个 CPU 逻辑核心忙碌时间/真实秒，但不是本模块独占，不含 GPU、第三方应用独立进程。新增纯算术诊断，不采样、不唤醒、不轮询。
- 不存在「关闭工作台、相同亮度刷新率/任务/环境、断开电源」对照；不能证明这些负载全部由模块产生，也不能证明没有额外能耗。
- `SystemUiPanelMonitor.changed()` 在高刷新率面板的每个 pre-draw 被调用，之前无论状态是否变化都会重新调用菜单 gate。已限制成真正 OPEN/CLOSED/UNKNOWN **状态变化**才触发 gate，保留监听和原生手势输入，降低无用 UI 工作，不据此宣称全部 CPU 问题解决。
- 原 500ms 锁屏 fallback 和 PR #16 息屏候选仍需单独验证：该候选改变锁屏虚拟显示输出热身与解锁等待，存在状态恢复权衡，**没有未经真机证据直接混入本轮**。

## 4. 通知栏仍非完美

- `ShadeRegression.kt:155`：Android 15 AOSP 模拟器 Quick Settings 第二次打开后，连续两次原生上滑仍由 `NotificationShade` 获得焦点。
- 模拟器**没有注入 ColorOS/Vector 模块**；这项失败说明 AOSP 侧测试存在问题或手势/ROM差异，**不是** ColorOS 真机手势已修复的证明，更不能删掉失败断言伪造全绿。
- 用户真实手机曾反馈「下拉后必须先点顶部空白才能收回」，在 Ace 7 Pro + N5 + Y700 的通知栏/控制中心与三点菜单互斥、滑动手势均须独立复验。
- 保持原生通知栏系统负责触控，不给它叠加新的全屏遮罩或强制坐标变换。

## 5. 不得跨越的发布闸门

- GitHub CI：真实 Android 编译、JVM、源码冻结脚本、包内 release-history 读取、HWUI 表面与菜单/原生通知栏检查记录必须可核对；失败或环境不支持要明确分类和阻塞。
- 一加 Ace 7 Pro PMS110：1/2/3/4 个小窗等比放大、2→3→4 与反向动画、主窗几何、加号/菜单、主小窗交换、通知栏底部回收手势，连续操作无残影/错位。
- N5：折叠和展开的主窗口优先/平行视窗/侧栏自动隐藏恢复/快捷栏，原稳定部分不被 Ace 专属动画覆盖。
- Y700：横屏左/右/顶部布局、竖屏安全 inset 与加号跟随、原生壁纸保持完整，不强制横向拉伸竖屏任务。
- 内容连续性：抖音/小红书暂停→切换后不主动恢复播放，播放→切换不主动暂停，返回不主动刷新；不能冻结任务、重建虚拟显示或模拟私有点击。
- 性能：不插电、两组对照（开启/关闭台前调度），相同设备/任务/亮度/刷新率/时长；记录温度、净电量变化与 SystemUI CPU 同类型指标、卡顿；不能承诺“零耗电/零发热”。
- **必须采用新版本号和递增 versionCode 且与现装证书一致**，核对 APK 文件本身和下载路径真能访问；用户没有终端操作义务。
- 未达到上述门槛：保留 Draft 和真实失败记录，无正式 APK 交付、不声明完美。
